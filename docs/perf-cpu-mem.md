## 1. ★ 为修 LLM 做的全部改动（**这是本版最重要的前提变化** ✓）

**根因链**（每步都有铁证 ✓）：

1. buildroot 的 `.config` 里 **`# BR2_GCC_ENABLE_OPENMP is not set`** ✗
2. ⇒ 交叉 `g++ -fopenmp` 报 **`cannot read spec file 'libgomp.spec'`** ✗
3. ⇒ `llama.cpp` 的 CMake **`GGML_OPENMP_ENABLED:INTERNAL=OFF`** ✗
4. ⇒ ggml 退回自带线程池 ⇒ **实测 1 token/秒**（文档基准：整句 2.3 s）

**改动**（都在 PC/SDK 侧，**不动产品代码** ✓）：

| # | 改动 | 结果 |
|---|---|---|
| ① | 两棵构建树的 `.config` ＋ SDK 片段 加 **`BR2_GCC_ENABLE_OPENMP=y`** ✓ | `--enable-libgomp` 进了 gcc 的 configure ✓ |
| ② | **重建 gcc**（`make host-gcc-final`，⚠ 必须重新 configure ⇒ **不能只用 `-rebuild`** ✗） | 产出 aarch64 **`libgomp.so.1`** ＋ `omp.h` ＋ `libgomp.spec` ✓ |
| ③ | 重编 llama.cpp（⚠ **`-DLLAMA_SERVER_UI=OFF`** —— 否则它会联网下 Web UI 而超时 ✗） | **`NEEDED [libgomp.so.1]`** ✓ 铁证 |
| ④ | 上板：`llama-server` ＋ 全部 `.so` ＋ **`libgomp.so.1`** 装进 `/usr/lib/assistant/llm/bin/` ✓ | `/proc/<pid>/maps` 里**真有 `libgomp.so.1`** ✓ |

**实测收益** ✓：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `prompt eval` | 662.5 ms/token（**1.51 tok/s**） | **104.1 ms/token（9.60 tok/s）** ⇒ **6.4×** ✓ |
| `eval`（逐 token 生成） | 1062.8 ms/token（0.94 tok/s） | **1062.8 ms/token（0.94 tok/s）** ⇒ **没变** ✗ |

> ★ **重要区分** ✓：**预填充（矩阵乘密集）吃到了 OpenMP ✓；逐 token 生成是**内存带宽瓶颈** ✗**，
> 与线程数无关 ⇒ **0.94 tok/s 是硬件约束，不是配置问题** ✓（如实记录，不再当"没修好" ✗）。

### 3.2 ★★ 「双输入」这个因子**真的差一倍多**（A3 vs A4）

| 场景 | CPU 均 | CPU 峰 | 温度峰 |
|---|---|---|---|
| **A3 键盘源** | **64.2** | 99.5 | 50.0 |
| **A4 命令行源** | **29.8** | 95.3 | 43.1 |

⇒ **原因** ✓：`gui.input_source=keyboard` 时 GUI 会拉起**虚拟键盘**（`QQuickWidget` 渲染 QML ✓）
⇒ **显著多耗 CPU** ✓。⚠ 命令行源下 GUI **不弹键盘** ⇒ 几乎回到基线 ✓。

> ⚠ **更正一条我先前的错误判断** ✗：我曾据"两份 CSV 字节数相同（8647 B）"断言
> 「输入源对 CPU/内存影响极小」✗ —— **错了** ✓。字节数相同是巧合 ✓；
> **内容差异显著**（64.2 vs 29.8 ✓）。教训 ✓：**不能拿文件大小代替内容比对** ✗。

## 4. 结论（**五条** ✓）

1. ✅ **无持续内存泄漏迹象** ✓：**27/32** 个场景 `Δagent` 在 **±6 MB** 内 ✓；
   ⚠ **但 SigLIP 首次加载会一次性 +400~800 MB** ✓（3.4 ✓），**且未做小时级验证** ✗。
2. ★★ **「双输入」因子的差异是本次最大发现** ✓：**键盘源 CPU 均 64.2% vs 命令行源 29.8%** ✓
   ⇒ **虚拟键盘渲染的代价** ✓（3.2 ✓）。
3. ★ **LLM 是最重的负载** ✓：CPU 均 **39.5%**、温度峰 **52.5 °C**、`load1` 峰 **6.00** ✓；
   **prompt 已随 OpenMP 修复快 6.4 倍** ✓，**decode 0.94 tok/s 是内存带宽瓶颈** ✓（§1 ✓）。
4. ✅ **SigLIP/NPU 通路打通** ✓：**NPU 峰 66–67%** ✓（学习监督／游戏检测 ✓）——
   旧版「NPU 全程 0%」的结论**已作废** ✓。
5. ⚠ **串流已全程连接** ✓（`connected(7)` ✓），**待机基线 CPU 均 27.4%** ✓ ——
   ⚠ 与旧版"无串流 3–5%"不可比 ✗：**本版才是真实使用态** ✓。
