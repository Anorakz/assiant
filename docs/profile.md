# 用户画像：IP/歌手权重 + 当前心情（Phase 7 T9 建，T10 消费）

> **一句话**：Agent 自己攒一段"纯对话"，攒到 **2000 字**就归纳一次 —— 用户对**壁纸 IP**、
> **歌手**的喜好（权重）与**当前心情**（问一次模型），写一行到 `config/user_profile.jsonl`。
> **它不是工具**：模型看不到、也调不到它（T9 定的）；**T10 起 Agent 在挑图/补歌/判负反馈
> 三处读它**（§8），模型那边依然一无所知。

---

## 1. 三个边界（先说清，免得误会）

| 不是 | 是 |
| --- | --- |
| 不是模型上下文的一部分 | 那段"纯对话"只在**内存**里（`agent/core/chat_memory.py`），板端 LLM 每轮本来也无状态 |
| 不是工具 | 不进 `TOOL_MODULES`、权限表没有它、prompt 清单**一个字符都不涨**（清单仍是 3522/3600） |
| 不是"应用的入口" | 画像**没有对话入口**（模型看不见、调不到）；但 **T10 起 Agent 自己会消费它** —— 挑"下一个"壁纸、补歌、判负反馈、心情变了重置队列。谁读它、读来干什么见 §8 |

## 2. 纯对话记忆（T9-1）

- 只收**纯对话**：`source ∈ {gui, terminal}`。定时提示（scheduler）、测试注入、系统消息都不算。
- 每条记 `role / text / ts / **state**` —— `state` 是**说这句话时**板子在哪个模式（idle/study/game/sleep），
  这是判心情的**场景**依据。
- 有界：8000 字 / 80 条（挤掉最老的）；单条超预算只留它**最近**的一半（`truncated=True`）。
- **不落盘**（你定的）：进程退出即无。**触发口径是 `pending_chars()`**（自上次构建以来攒的，
  被挤掉的老条目也算"攒过"）；`settle()` 归零它，但**保留最后 6 条**在内存里给下一个画像当上下文。

> ⚠ 踩过的坑（接线时测试抓到）：如果拿"内存里一共多少字"当触发口径，**保留的那 6 条自己就可能
> 超过 2000 字** → 每轮都满足条件 → 构建一遍又一遍。所以触发只认"自上次构建以来"。

## 3. 前两路：权重（不是计数）

```
壁纸 IP:  权重 = 0.6×用量占比 + 0.3×提及占比 + 0.1×近期占比
歌手:     权重 = 0.7×播放占比 + 0.3×提及占比
```

| 项 | 怎么来的 |
| --- | --- |
| 用量（命中张数） | 用户换过的图里, 有几张排在"最像该 IP"的**前 K 名**（K = 用户用过的张数, 最少 3）：锚点原型向量 + `TagIndex` 纯 CPU 余弦 |
| 播放 | `config/music_library.jsonl` 的 `plays` × `tags.artist`（歌手轴是自动标签之一） |
| 提及 | 这段纯对话里说到这个名字的次数（只数**用户**说的） |
| 近期 | 30 天内线性衰减（1 → 0，更早算 0） |

> ⚠ **"命中"为什么是"排在前 K"而不是"在候选里"**：`TagIndex.match("ip=…")` 给的是
> **全库按相似度排序**（40 张库就是 40 个候选，不是筛过的集合）—— 所以"像这个 IP"只能是
> "排在前面"这件事。板端 T9-4 实测把这个口径定死：K 取"用户用过几张"，含义就是
> "在 40 张里最像它的那几张里，用户用过几张"。
>
> ⚠ 锚点是**文件名**（相对 `wallpaper.dir`）：目录/锚点配错时检索会直接报错。
> 那种情况**不许静默算 0** —— 记录里 `walls.anchor_problems` 会写清是哪个 IP、为什么
> （板端 T9-4 就是靠这条发现"IP 权重一直是 0"的，见下）。

- "占比"= 该项 ÷ 所有候选的和 —— 所以权重回答的是"谁**相对**更重"，不是绝对次数。
- 每行都留了**分子分母**（`parts.hits / mentions / recency / usage_share / mention_share / recency_share`），
  能照着复算；配方在 `agent/core/user_profile.py` 顶部两个常量里（`IP_WEIGHTS` / `ARTIST_WEIGHTS`）。
- 样本薄（换图 / 音乐库 / 对话 任一项 < 3）→ 记录里 `thin` 列出来，`mood.confidence` 直接降成 `low`。

## 4. 负反馈 = **两层清零**（你定的）

用户说"不想听 X 了 / 别看 X 了 / 听腻了 / 换掉 X"（**负向词 + 实体名同时出现**才算）：

1. **画像层**：该实体的权重与所有分量归 0，记 `muted_at` + `muted_text`（那句原话）。
2. **源文件层**：那些图的 `used`/`last_used`（`wall_data.jsonl`）、那些歌的 `plays`/`last_played`
   （`music_library.jsonl`）**也清 0** —— 走那两个模块自己的唯一写者
   （`wall_data.clear_usage_in_file()` / `music_library.clear_plays()`）。
3. **继承**：`muted` 名单存在画像记录里，每次重建都**重新套用** —— 否则源文件里新长出来的用量
   会把它顶回来。

> ⚠ **副作用是你明确要的设计意图**：清零之后那张图/那首歌重新变成"用得/听得**最少**的"，
> 于是下次说"挑一张用得最少的/放一首听得最少的"会**先把它们挑出来**（= 归零之后重新进候选）。
> 有测试钉着这条语义（`tests/test_user_profile.py`）。
>
> ⚠ 只认**认得出来的实体**：对不上名字就一条都不产生（宁可不猜）。

## 5. 心情：**问一次模型**（唯一一次模型调用）

- 提示词带三样：那段纯对话（`ChatMemory.excerpt()`，每条前面带 `[study]` 这种**场景**标记）、
  这段对话里出现过的模式、现在几点；并要求**只回封闭词表里的一个词**：
  `focused 专注 / relaxed 放松 / happy 开心 / tired 疲惫 / stressed 烦躁 / calm 平静`。
- 解析**严格**：回一整句话、或同时出现两个词 → `unknown`；模型炸了/超时 → `unknown`（原话记在
  `mood.raw`，原话里的错误记在 `mood.error`）。**判不出就说判不出，不编。**
- **判心情失败不算构建失败**：记录照落一行，只是 `mood.label=unknown`。
- `mode=cloud` 时这一步会**把那段对话摘录发给云**（与用户每轮发言本来就发云是同一性质）；
  记录里 `mood` 会带上这次用的模式，便于事后回溯。

## 6. 触发与并发（T9-3）

- 触发者**只有 Agent 一个**：`Runtime.handle_event` 每轮答完走一次 `_profile_tick()`，
  `pending_chars() ≥ profile.trigger_chars`（默认 **2000**）或 `pending_turns() ≥ trigger_turns`
  （默认 12，兜底）就起一个**后台任务**。用户在对话里说什么都触发不了它。
- 构建在后台：**不堵对话**（有测试）。一次只跑一个；失败只记 warning、**不结算**、
  60 秒内不重试（免得每轮都去问一次模型）。
- 构建完 `settle()`：触发计数归零（保留最后 6 条在内存里）。
- ⚠ **真实代价**：板端 llama-server 是**单进程**，那次判心情的调用会和用户下一轮**排队** ——
  实测数字见 §8。

## 7. 配置与文件

```yaml
profile:
  enabled: true
  trigger_chars: 2000      # 自上次构建以来攒到这么多字就构建一次
  trigger_turns: 12        # 兜底: 短消息太多时按轮数触发
  # file: config/user_profile.jsonl   # 默认就在这儿; 相对路径按仓库根
```

- 画像文件：`config/user_profile.jsonl`（**一次构建一行**、原子写、本模块是唯一写者；
  进 `.gitignore`；写入者白名单里的第 5 个 —— 见 [`config-sources.md`](config-sources.md) §2）。
- **记录里没有对话原文**（只留 `mood.excerpt_chars` = 看了多少字）。唯一留下的原话是
  `muted_text` —— 那是"把源文件计数清 0"这个破坏性动作的凭据。
- 一条记录长这样（字段说明）：

| 字段 | 含义 |
| --- | --- |
| `built_at` / `trigger{reason,chars,turns,threshold}` | 什么时候、因为什么构建的（字数还是轮数，攒了多少） |
| `samples{wall_tagged,wall_images_used,tracks,plays,chat_turns,chat_chars}` | 样本量（权重与心情的置信度都看它） |
| `walls.ip[]` | 每个 IP：`weight` + `parts` + `last_used` + `images`（命中的那几张） |
| `walls.anchor_problems{}` | 哪个 IP 的锚点检索不了、为什么（**不许静默算 0**） |
| `music.artist[]` | 每个歌手：`weight` + `parts` + `last_played` + `tracks` |
| `mood{label,zh,ok,confidence,excerpt_chars,raw,error,ms,prompt_chars}` | 心情与这次模型调用的实情 |
| `feedback[]` / `unmatched_feedback[]` | 这次识别到的负反馈（以及认得词但认不出实体的情况） |
| `muted{ip[],artist[]}` | 累积的"不想看/听"名单（下次重建时重新套用） |
| `cleared{wall_images,tracks}` | 这次真清掉了几张图 / 几首歌的计数 |
| `thin[]` | 哪些样本太薄（提醒别当结论） |

## 8. 消费方：画像怎么被用掉（Phase 7 T10）

> T9 定的口径是"画像暂不应用"，**T10 起接上了**。这一节是"谁读画像、读来干什么"的清单 ——
> 画像本身在 T10 里**一个字都没改**（还是 T9 那份记录格式与生成逻辑），变的是**读它的人**。

**一句话**：画像只被 **Agent 自己**在**三个地方**读；模型那边**依然一无所知**
（不进 prompt、不是工具、权限表里没有它）。

| 消费方 | 读哪些字段 | 干什么 | 代码 |
| --- | --- | --- | --- |
| **挑壁纸的"下一个"** | `walls.ip[]` 权重、`mood.label` | 没给 `match`/`sort` 时按画像给候选排序取第 1 名；画像太薄就退回文件名顺序 | `Runtime._choose_next()` / `_rank_next_by_profile()` |
| **补歌队列** | `music.artist[]` 权重、`muted{artist,track}` | 本地库按歌手偏好排序；不够时**只按画像里的歌手**去 PC 搜；"不想听"的歌手/歌**永远不补** | `Runtime._music_autofill()` → `MusicPlayer.refill()` |
| **画像构建本身**（自消费） | 上一次的 `muted{}` | 负反馈名单**跨次累积**：这次没提到、但上次说过"不想听"的，仍然清 0 | `user_profile.build_profile()` / `muted_from_records()` |

### 8.1 挑壁纸的权重配方（T10-2）

```python
RANK_WALLPAPER_WEIGHTS = {"ip": 0.7, "mood": 0.2, "fresh": 0.1}   # 画像在 user_profile.py
```

| 项 | 怎么算 | 为什么这么算 |
| --- | --- | --- |
| `ip` | 候选图在画像 `walls.ip` 里的**权重**（IP 相似度用**排序名次代理** `1 - rank/N`，池子按 IP 缓存） | 画像里存的是"你喜欢过哪些 IP"，不是"这两张图像不像"；名次代理不需要再过 NPU，也不需要标定余弦阈值 |
| `mood` | 当前心情 → 一个或多个词表里的 `mood` 标签（`MOOD_TO_TAGS`）→ 命中加分 | 心情好/累 想看的图不一样 —— 这是唯一"当下"的信号 |
| `fresh` | 这张图**没被用过** / 少用 → 加分 | 不然画像会一直推同一张"最像的" |

- **心情是 `unknown` 时 `mood` 那一项不给分**（`mood_tags()` 返回空），但没有别的惩罚 ——
  只是"这一项缺席"，`ip`/`fresh` 照算。
- **画像太薄时整个画像不参与**（`profile_basis()` 看 `thin[]`），走文件名顺序回退。
  理由见 [`tagging.md`](tagging.md) §6.2：回退行为要**可预测**。
- 壁纸 `match` / `sort` **优先级高于画像**：你点名了条件，画像就不插手。

### 8.2 补歌的权重配方（T10-4）

```python
RANK_TRACK_WEIGHTS = {"artist": 0.7, "mood": 0.2, "fresh": 0.1}   # 注意是 artist 不是 ip
```

- `artist` = 画像里该歌手的权重（配方的第一部分见 §3）；`mood` 同上（心情 → 标签）；
  `fresh` = 没播过/少播加分。
- **"不想听"是硬过滤，不是减分**：`muted{artist,track}` 里的东西**直接不进候选**
  （`muted_artists=` / `muted_tracks=` 一路传到 `rank_tracks()` 与 `refill()`）。
- 队列补到 `music.autofill.target`（默认 **30**）；**不够时只按歌手去 PC 搜**，
  这条是你 T10 验收时明确的口径（`增加补歌行为，但是补歌只会根据歌手补`）。
  细节见 [`music.md`](music.md) §4.4。

### 8.3 心情变化 → 重置队列（T10-5）

- 判据：**两个已知心情不同**才算"变了"；`unknown` 不算（模型偶尔答不出不该清队列）。
- 重置时**留住正在放的那首**在队首，其余清掉、按新心情补满。
- 负反馈点名的那一批**立刻**从队列里去掉（正在放的那首也去，并跳下一首）。
- 用户的第 6 条决定原话：`只有心情变化的时候才重置队列`。细节见
  [`music.md`](music.md) §4.5。

### 8.4 板端实测（T10-6 验收）

跑法（板端, 仓库根）::

```bash
python3 tests/board/t10_accept.py          # 只验机制（不调模型, 心情=unknown）
python3 tests/board/t10_accept.py --llm    # 起本机 llama-server, 真的问一次心情
```

**四件都真跑了**（真壁纸目录 40 张 + 真标签索引 + 真音乐库 + 真画像, **全在副本上跑**）:

| 验的什么 | 板端原文 | 说明 |
| --- | --- | --- |
| **画像在挑图** | `画像挑出来的『下一个』: wallhaven-858vpj_1200x1920.png（basis=profile; 像 SNF（0.70）；还没看过）` | `ip 0.7` 那一项的命中理由写在 `why` 里, 用户/日志看得见 |
| 画像不可用 | `basis=order / 回退: 按文件名` | 把画像文件挪走 -> **退回文件名顺序**（不是"用得最少的"） |
| **负反馈清队列** | 点名 `高橋洋子` -> `affected` 10 首; 队列里 4 首被移出, **补回 6 首且没把那 4 首补回来** | 队列变成 `宇多田ヒカル/米津玄師`; "类似的全部"真的清干净了 |
| **只有心情变了才重置** | `心情从 happy 变成 tired -> 重置队列（清掉 6 首, 留住正在放的 1824020873）`; 心情没变 / `unknown` -> `None` | 留住的确实是"正在放的那首" |
| **正在放的那首被移出就跳走** | `开始播放 2060973088 地球儀`（在"不想听的 5 首已从队列里去掉"之后） | 用户说"不想听"却继续放它 = 骗人, 所以当场跳下一首 |
| **端到端（真触发）** | 攒 `259 字 / 4 轮`（触发线临时 60 字）-> 后台构建 `12.4~27.2s` -> 副本画像 **+1 行**; `--llm` 两次跑: `心情=calm/平静 置信=medium`（判心情 15.6s）与 `心情=unknown`（模型答不出就如实记 unknown） | 触发 -> 构建 -> 落盘 -> 重挑 next + 队列动作 是一条链 |
| **记录里没有对话原文** | 同一批对话里那句无关的"我家的猫叫豆豆"**不在**记录里（`mood.excerpt_chars=349` 只记长度） | 唯一留下的原话仍是"不想听 X"那句凭据（`muted_text`） |
| **真数据一个字节没动** | 三个 `config/*.jsonl` 跑前跑后 `md5` 逐个相同 ✔ | 负反馈会真清源文件计数（T9 的设计）, 所以验收**只动副本** |

⚠ 验收脚本自己踩过、也写进脚本注释的两个坑（都不是产品问题）:

1. `tags.artist` 是**列表**不是字符串 —— 探针里当 str 用会选出一个不存在的歌手名;
2. 负反馈之后**立刻补歌**读的是**已落盘的**画像（`muted` 名单在里面）: 生产路径的顺序是
   `append_record()` **先**、`_apply_profile_effects()` **后**（`_build_profile_task()`）。
   验收脚本里要是反过来调, 就会看到"刚去掉又被补回来" —— 那是**脚本的错序**, 不是补歌的 bug。

跑法与原文记录另见本地工作记录 `todo.md` 的 T10-6 一节。

**而且不报错**（画像里的 IP 权重只剩"提及"那一项）。修完板端复跑：`SNF` 命中 1 张 ✓。
同一轮还修了两处口径：命中改成"排在前 K"（见 §3）、锚点报错写进 `walls.anchor_problems`；
另外 `mood.ok` 以前在模型回 `unknown` 时是 `True`（"判出来了"），现在只有真的给出六词之一才算 ✓。

## 10. 已知边界（如实写）

- **权重配方是"第一版口径"**（0.6/0.3/0.1 与 0.7/0.3 是人定的），不是拟合出来的；样本少时排序晃动很正常。
- **IP 喜好受锚点质量限制**：一个 IP 只有 1–2 张锚点时，"像不像"本身就不稳（见
  [`tagging.md`](tagging.md) §8 的 IP 检索实测）。
- **心情是 0.6B 判的**：它只在一个封闭词表里选一个词，实测仍会回废话（那时记 `unknown`）；
  别把 `confidence=low` 的心情当结论。
- **清零不可逆**（设计如此）：源文件里的 `used`/`plays` 被清 0 之后没有历史可恢复
  （只留 `.bak`，那是上一次写的备份）。
- **画像挑图用的是"名次代理"**（§8.1）：`ip` 那一项拿"排在第几"当相似度，不是真余弦 ——
  所以画像能说的只是"这几张里更靠前的那张"，**别把它读成"这张特别像"**。
- **画像排序会随样本晃动**：样本薄（`thin[]` 非空）时名次本来就跳，所以代码里留了
  "画像太薄就退回文件名顺序"这条 —— 回退行为**可预测**比"每次都不一样"重要。
- **心情变了会清队列**（§8.3）：这是你定的第 6 条，代价是手动排过的歌只剩正在放的那首。
  想要"别动队列"就别在这期间换心情话题 —— 目前**没有"别重置"的开关**（如实写下来）。
